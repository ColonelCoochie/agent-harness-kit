# Research-validated harness review

Date: 2026-08-01

## Claim boundary

This review separates three different claims:

1. **Mechanism works:** deterministic tests demonstrate the intended local invariant.
2. **Mechanism is safer or faster:** a controlled before/after experiment demonstrates an engineering improvement on the same observable outcome.
3. **Harness improves coding-agent outcomes:** randomized agent episodes with an external sealed oracle demonstrate better safe completion. The current repository does not yet have enough episodes for this third claim.

Literature motivates hypotheses; it does not by itself prove that a repository change is beneficial. Every adopted change below therefore needs a failing pre-change reproduction and a passing post-change result. Ideas without that evidence remain deferred or rejected.

## Baseline

- Standalone repository: `ColonelCoochie/agent-harness-kit` at v0.5.0 commit `3f3f2a6`.
- Runtime: zero-dependency Node.js 20+; measured here with Node.js 22.17.0 on Windows.
- Existing conformance suite: 40/40 passing in 55.615 seconds and 49.531 seconds on two independent runs.
- Required syntax checks: reusable initializer core and generated runtime both pass.
- Local `npm` launcher is broken because its global `npm-cli.js` is absent. Direct `node --test` is the authoritative project check on this host; this is an environment defect rather than a repository failure.
- The kit is now self-hosted with its own `.harness/`; `doctor` passes and the structural audit scores 98/100 before the first evidence record.

## Fifty separately prompted research lanes

All lanes use `gpt-5.6-sol` at `xhigh` reasoning. At most three researchers run concurrently because the platform exposes four total slots including the coordinating agent. Researchers are read-only and must return primary sources, a causal hypothesis, a falsifiable test, and rejection criteria. Searches explicitly cover Google Scholar, JSTOR, arXiv, and the primary ACM, IEEE, USENIX, standards-body, and publisher archives relevant to each lane. These are separately prompted perspectives from one model family, not statistically independent replications; agreement among them is hypothesis support rather than outcome evidence.

## Adopted experiment: mutation-lock ownership

### Causal reasoning

The v0.5.0 lock declared a directory recoverable whenever it was older than 300 seconds, even when `owner.json` named a PID that was still alive. The default verification timeout is 600 seconds. Therefore an ordinary long verification could be overlapped by a second mutation. The original owner also removed the lock directory recursively in `finally`, regardless of whether it still owned that directory.

### Pre-change result

`node --test tests/state-lock.test.mjs` on the v0.5.0 algorithm:

- live-owner age test: failed because the competing mutation succeeded;
- ownership-release test: failed because the replacement lock was deleted;
- result: **0/2 passing**.

### Treatment

- Assign a random acquisition token and persist it with the owner PID.
- Recover automatically when a known owner PID is dead.
- Use age only when ownership is unknown, never to evict a known-live owner.
- Release only when the current owner token equals the token returned by acquisition.
- Remove the owner file and then the empty directory instead of recursively deleting an unverified lock instance.

### Post-change result

The same focused suite passes **2/2** in 0.783 seconds and 0.821 seconds on two runs. The existing dead-owner recovery regression remains part of the full suite and must pass before release.

The expanded conformance suite passes **42/42** in 49.438 seconds and 49.257 seconds. The self-hosted `full` gate independently passes 42/42 in 49.381 seconds, and both reusable source files pass Node syntax checks. These samples show no observed suite-time penalty relative to the 49.531-second baseline run; they are not a statistical performance claim.

### Residual boundary

The token prevents an ordinary owner from deleting a different lock instance, but it is not a distributed lock service and cannot constrain arbitrary direct filesystem edits. Simultaneous crash recovery and multi-file crash consistency remain separate experiments.

## Adopted experiment: committed scope history

### Causal reasoning

The v0.5.0 scope baseline stored only dirty `git status` entries. A feature could change an out-of-scope tracked file and commit it after `start`; the worktree would become clean and verification would see no changed path. Binding a newly started feature to its exact Git commit and unioning the reachable tree diff with final staged unstaged and untracked state closes that specific false-pass route.

### Pre-change result

`node --test tests/scope-history.test.mjs` against the status-only algorithm passed **1/5** controls. It falsely accepted a committed forbidden file omitted a committed allowed file from evidence missed both sides of a committed rename and accepted unrelated rewritten history. The only passing control preserved dirty content that existed before feature start.

### Treatment and post-change result

- Record the exact start `HEAD` with the scope baseline for newly started features.
- Require the current `HEAD` to descend from that commit.
- Union committed additions modifications deletions and both rename endpoints with final worktree/index/untracked changes.
- Exclude baseline-dirty bytes that were merely committed unchanged.
- Preserve legacy active features that predate the new field instead of inventing a historical baseline.

The same focused suite passes **5/5** in 7.385 seconds and the reusable runtime passes its syntax check.

### Residual boundary

This detects net changes reachable from the recorded start commit plus sampled final repository state. It does not prove transient writes that were restored before sampling or commits erased from reachable history; those require an external observer or OS-enforced boundary.

## Adopted experiment: fail-closed command environment

### Causal reasoning

Configured commands normally receive only `security.environmentAllow` plus explicitly requested provider credentials. The v0.5.0 executor instead fell back to the complete parent `process.env` when that allowlist was missing or null. `doctor` reported malformed configuration but direct `check` or `verify` did not run that validation before command execution.

### Pre-change result

`node --test tests/environment-boundary.test.mjs` passed **2/5** controls. Missing and null allowlists launched the configured probe with the ambient canary. A wrong-type value failed only later through an unrelated `.filter` exception rather than a stable pre-spawn policy check. Explicit empty policy and opt-in provider injection were the two passing controls.

### Treatment and post-change result

- Validate `security.environmentAllow` at the configured-command boundary before secret collection credential resolution or process spawn.
- Leave internal fixed Git probes on their separate internal environment path.
- Preserve an explicit empty allowlist as valid and preserve explicitly requested provider injection.

The same focused suite passes **5/5** in 6.002 seconds and the runtime passes its syntax check. All three malformed shapes reject with zero spawned marker zero verification attempt and zero evidence record; the empty and provider controls still pass.

### Residual boundary

An environment allowlist reduces ambient disclosure but does not confine filesystem network or descendant-process behavior. This treatment supports a fail-closed configuration claim only—not a sandbox or DLP claim.

## Adopted experiment: lossless repeatable CLI values

### Causal reasoning

The runtime used one generic `list()` helper for both comma-separated identifiers and opaque user values. It therefore split ordinary commas inside acceptance prose shell commands and filesystem globs. The mutation could remain silent when criterion and command comma counts happened to match.

### Pre-change result

`node --test tests/cli-values.test.mjs` passed **3/8** controls. CSV dependencies verification levels and credential providers behaved as documented. The runtime corrupted the exact criterion command allow and deny round trip broke a comma-bearing script command broke repeated criterion-command pairing split repeated globs and failed to enforce a deny path containing a comma.

### Treatment and post-change result

- Preserve each repeated criterion command allow and deny argument as one trimmed opaque value.
- Continue comma splitting only for documented identifier lists such as dependencies levels and credential providers.
- Preserve repeated-flag order and criterion-command pairing without adding a parser dependency.

The same focused suite passes **8/8** in 6.119 seconds and the runtime passes its syntax check. The behavioral probe executes a script and writes a path containing commas while the exact comma-bearing deny control now blocks.

### Residual boundary

This is a compatibility-first correction to feature-creation values. It does not add a schema-aware CLI parser reject every unknown option or change the initializer's explicitly documented `--commands` CSV interface.

## Post-synthesis release correction: Node 20 test discovery

### Causal reasoning

The expanded test script initially passed `tests/*.test.mjs` to Node. That happened to work under the local Node 22 runner, but the package declares Node 20 support and Windows shells do not provide a portable wildcard-expansion contract. The [Node 20 test-runner documentation](https://nodejs.org/download/release/v20.15.0/docs/api/test.html) explicitly guarantees recursive native discovery when `node --test` receives no paths, including `.test.mjs` files.

### Pre-change result

`node --test tests/test-command.test.mjs` passed **0/1**: both `package.json` and the self-hosted full gate contained `node --test tests/*.test.mjs`, contrary to the shell-independent command asserted by the supported-runtime regression.

### Treatment and post-change result

- Use `node --test` in both the package script and self-hosted full gate.
- Keep a focused regression that rejects wildcard-bearing full-test commands.
- Run the entire suite with the official checksum-verified Node v20.20.2 Windows x64 binary as well as the local Node v22.17.0 binary.

The focused suite passes **1/1**. Native discovery passes **61/61** on Node v20.20.2 for Windows and **61/61** on Node v22.17.0. The downloaded Node archive matched the SHA-256 value in the release's official `SHASUMS256.txt` before execution.

### Residual boundary

This proves native discovery for the tested latest Node 20 Windows release and the local Node 22 release. It does not certify every historical Node 20 patch or every supported operating system; the documented no-path discovery contract supplies the compatibility basis for those unexecuted combinations.

## Outcome-evaluation protocol (not yet an outcome claim)

The preregistered primary comparison is full harness versus guidance-only, with ordinary repository state as a secondary control. Each task/model/repetition gets isolated clean clones, fixed budgets, randomized arm order, no shared transcript or solution cache, and an evaluator unavailable to the agent during work.

Primary endpoint:

```text
safe_external_completion =
  hidden_feature_behavior
  && hidden_regressions
  && restartability
  && no_forbidden_changes
  && no_canary_secret_persistence
```

Report safe-completion risk difference, false-completion risk, continuity success, tokens, wall time, cost, tool calls, and boundary violations separately. The first pilot is 12 tasks × 4 repetitions × 2 principal arms = 96 episodes. Until that or an equivalent controlled study runs, the repository may claim mechanism correctness and measured engineering improvements only—not a causal increase in coding-agent success.
